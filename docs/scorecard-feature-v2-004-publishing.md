# Scorecard Feature v2 — Ticket #004 Publishing & Correction

## Objective

Move Scorecard administration away from arbitrary/manual publication toward named, fully closed Month / Quarter / Year periods, retain one-person generation only as a recovery fallback, and add a narrow authorized correction workflow that creates immutable revision history rather than mutating a finalized Scorecard.

## Implemented behavior

### Closed named periods

- Admin publishing uses canonical named closed periods generated by `recentClosedScorecardPeriods`.
- The UI no longer asks an administrator to type arbitrary period start/end dates.
- The server derives the canonical end/label from the submitted kind/start and re-validates that the period is closed in America/Chicago time.
- Month, Quarter, and Year boundaries remain the existing canonical Scorecard boundaries.

### Publishing model and recovery fallback

- `/admin/scorecards` presents period publishing as the normal model.
- Period-wide publishing is explicitly described as the temporary pre-automation fallback; the existing 40-card live guard remains intact.
- One-person generation is under `Fallback publishing tools` and relabeled `One-person recovery`.
- Recovery remains limited to one initial Producer/Builder card for a canonical closed period and is not presented as a way to overwrite an already-published card.
- The fallback `<details>` stays collapsed on an ordinary page load, but automatically opens when recovery query params, a recovery error, or a recovery result are present so the relevant status/action is not hidden after navigation.

### Immutable correction workflow

- Admins can select the latest finalized, run-backed Scorecard revision and supply a required 5–500 character correction reason.
- The service independently re-checks admin authorization and the selected finalized snapshot.
- Correction lineage must match the same person, card type, canonical period, and immediately prior revision.
- A correction rebuilds the card from current canonical source truth; callers do not send replacement score values.
- Successful correction creates a new `corrected` snapshot revision pointing at the prior immutable snapshot.
- Prior snapshots are never updated or deleted.
- The normal Scorecard delivery outbox remains the delivery mechanism.

### Builder correction rank/population correctness

Targeted Builder recovery/correction must emit only one Builder artifact, but Builder `teamRank` and `recruitingRank` are organization-population metrics. The targeted path now separates artifact scope from frozen rank population context:

- the selected Builder is still the only generated/published Builder row;
- peer Builder rank facts are loaded from the latest finalized run-backed Builder snapshots for the same canonical period;
- the selected Builder's freshly recaptured Team IP / recruiting facts replace its prior facts inside that frozen peer population;
- `teamRank.population` and `recruitingRank.population` therefore remain the canonical eligible Builder population rather than collapsing to `1` during a one-card correction;
- the independent verifier recomputes the target Builder rank against the same frozen peer context before the corrected artifact can publish.

A focused correction regression proves a changed Builder can move from team rank `2/3` to `1/3` while recruiting rank remains `2/3`, with peer snapshots left immutable.

## SQL boundary / race safeguards

Migration: `supabase/migrations/20260903000100_scorecard_correction_workflow.sql`

`publish_manual_scorecard_correction` is `SECURITY DEFINER` but executable only by `service_role`. Inside the database boundary it:

1. Validates the correction reason.
2. Independently verifies `p_initiated_by` is currently an admin/super-admin.
3. Locks and validates a finalized, run-backed prior snapshot.
4. Re-validates the exact canonical calendar period.
5. Takes a transaction-scoped advisory lock for the logical next revision.
6. Rejects branching from a stale prior revision.
7. Converges only an exact logical retry: same normalized published payload, same correction reason, and same correcting admin.
8. Rejects a competing concurrent correction as stale rather than silently claiming its different audit reason was recorded.
9. Rejects a no-op correction before inserting a run.
10. Validates JSON envelope shapes before persistence.
11. Freezes a new targeted `scorecard_metric_run`, role fact, and exactly one metric row with prior-run lineage and correction reason.
12. Delegates immutable snapshot + delivery creation to the canonical `publish_scorecard_run` publisher.

The migration was **not applied or deployed** during Ticket #004. No Gateway or Rent-a-Mac operational changes were made.

### Timestamp-only no-op fix

Focused tests exposed an implementation bug: regenerated Producer metrics contain a new `generatedAt` timestamp, so a re-run with identical business values initially looked changed and created a revision.

The correction comparator now ignores volatile `generatedAt` metadata when deciding whether business-visible metric values changed. The SQL no-op/idempotency comparisons use the matching normalized published payload path (`metricPayload.preview.generatedAt`). A timestamp-only re-generation therefore produces no correction revision, while actual Scorecard metric changes still do.

## Server/action behavior

`correctPublishedScorecard`:

- calls the canonical `requireAdmin()` guard before service invocation;
- validates the snapshot UUID and correction reason at the action boundary;
- revalidates admin and member Scorecard archives after success/existing;
- surfaces `no_changes` without creating a revision;
- surfaces stale revision races as an actionable correction error.

The service maps a database stale-race exception back to `stale_revision`, and maps the SQL no-op guard back to `no_changes` rather than returning an opaque publication failure.

## Admin UX safeguards

Focused source-level UI assertions verify that:

- correction is shown before fallback tools;
- only finalized, run-backed snapshots are considered;
- the page chooses the latest revision per person/card/period identity;
- period publishing uses `periodSelection` and named closed periods;
- the manual selector contains no free-form date input;
- one-person generation is visibly framed as recovery rather than the normal path;
- fallback publishing tools are collapsed by default and auto-open for recovery selection/error/result state.

## Remaining operational considerations

- The correction RPC migration must be applied before deploying application code that invokes it. This Ticket intentionally does not apply/deploy the migration.
- The automatic Gateway-completion trigger for normal large-population period publishing remains a later automation step; Ticket #004 keeps the controlled closed-period fallback but no longer positions one-person generation as the normal workflow.
- The correction selector currently loads finalized run-backed snapshot history and reduces it to the latest logical revision in the application. This is correct for the current admin workflow, but if archive volume becomes very large it should move to a database-side latest-revision query/view for UI scalability.
